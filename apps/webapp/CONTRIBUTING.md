# Contributing to the AOW5 web app

This app is the site: the landing page, the **build planner** (`/builder`), and the farm tracker's
download page. [`README.md`](README.md) explains what it is and why it is built the way it is — read the
part covering the area you are touching before you change it. This file is the working agreement: how to
run it, what must not break, and what a pull request has to say for itself.

The tracker has its own: [`apps/tracker/CONTRIBUTING.md`](../tracker/CONTRIBUTING.md).

## Where your change belongs

| you want to change | it lives in |
|---|---|
| The board, slots, pickers, item details, sharing UI | `apps/webapp/src/` |
| Browsing, reading or saving a build | `apps/webapp/src/builds/`, `src/routes/Build*.tsx` |
| What the API returns, or a limit both sides enforce | `packages/aow5-api-contract` |
| The API itself | `apps/api` — a different app, with its own guide |
| The share-link codec, board state, types | `packages/aow5-shared/src/build/`, `src/types/` |
| Item/hero/ability data, icons, the id tables | nowhere by hand — regenerated by `parser/`, see below |
| The overlay itself | `apps/tracker/` — a different app |
| The tracker's page on this site | here, `src/routes/TrackerPage.tsx` — it is a page *about* the overlay |

Dependencies run one way: this app may import `aow5-shared`, and **may never import from
`apps/tracker`**. `/tracker` depicts the overlay rather than reusing it; that is the rule, not an
oversight.

## Setup

Node ≥ 22.18 and pnpm 9 (`corepack enable`). The extracted game data is committed, so nothing here needs
Dota installed.

```bash
pnpm install                        # from the repo root
pnpm --filter aow5-utils-webapp dev
pnpm --filter aow5-utils-webapp build
pnpm --filter aow5-utils-webapp test
```

Root scripts (`pnpm dev|test|build|check-types`) are Turborepo tasks across the whole workspace and are
what CI runs. Run all three before you push:

```bash
pnpm check-types && pnpm test && pnpm build
```

## The rules that break other people's links

A shared board is a URL somebody has already pasted into a chat. These four rules exist so it keeps
decoding, and a PR that violates one will be sent back:

1. **`data/id-table.json` and `data/ability-table.json` are frozen and append-only.** Never reorder,
   never remove. A dropped item stays as a tombstone; reordering silently repoints every link ever
   shared. Both tables are pipeline output — you append to them by re-running `parser/`, not by editing
   JSON.
2. **A wire-format change is a codec version bump**, and every older version must still decode. The
   version table and what each one meant are in the README's *How sharing works*. Golden tests pin the
   byte layout — add one for the new version rather than editing an existing one.
3. **The fragment belongs to the planner.** Routing is on `pathname` only. No in-page `#anchor` anywhere
   on the site: a stray `#data` that follows a visitor onto `/builder` gets decoded as a board and
   reported as a broken link. `navigate()` drops the fragment by default, and **exactly two callers may
   write one**: `redirectLegacyBuildLinks()`, and `openInPlanner()` — which is how a saved build is forked
   into the planner, and produces a URL indistinguishable from one shared by hand. A build's own page
   (`/builds/<slug>`) carries no fragment at all; its board comes from the API. That list of two is the whole
   list, and a third would need an argument in its own PR.
4. **Unknown means preserved, not dropped.** An index this build does not recognise renders as `?` and
   must re-encode to identical bytes, so a link from a newer build survives a round trip through an older
   one. Anything you add to the payload inherits that requirement.

## The other invariants

- **All three languages, always.** UI text goes in `src/i18n/strings.ts` (the planner) or `src/i18n/site.ts`
  (chrome, landing, tracker page), with an English, a Russian *and* a Chinese value — the type makes a
  missing one a build error. Chinese is the addon's own language, so where a string names something the
  game names too, copy the game's wording out of `locale.zh.*` rather than translating the English. No bare
  user-facing literals in JSX. The two files are separate because they change for different reasons — keep
  it that way.
- **Both themes, always.** Light and dark share one set of CSS variables; check your change in both. Item
  rarity tints are variables for exactly this reason — the dark palette's pastels are unreadable on white.
- **The previews are the real UI.** `BoardPreview` draws with the planner's own parts so tile size and
  rarity borders cannot drift. If you change a slot's look, check that preview rather than duplicating the
  change into it.
- **Motion stays cheap.** No `backdrop-filter` anywhere on the site, no new fixed blurred layers, and
  every animation pairs with `motion-reduce:animate-none`. The README records what the expensive version
  cost in scroll performance.
- **Dependencies need an argument.** The bundle being small is the reason the router is fifteen lines.
  shadcn/ui primitives are vendored into `src/components/ui/` — edit them in place, don't add a wrapper
  library. Do not vendor React Bits: it ships MIT **+ Commons Clause**, and keeping that out keeps this
  project's licensing simple.
- **Never hand-edit `packages/aow5-shared/public/data/` or `public/icons/`.** They are output. A data
  refresh is a `parser/` run and belongs in its own PR, separate from any feature.
- Don't commit `dist/`, `.turbo/` or screenshots — all gitignored, and a PR carrying them will be asked to
  drop them.

## Tests

`node --test`, no framework. The globs *are* the contract for where a test file may live:

| package | glob |
|---|---|
| `aow5-utils-webapp` | `src/lib/*.test.ts` |
| `aow5-shared` | `src/build/*.test.ts` — the codec, board state, golden payloads |
| `aow5-utils-api` | `core/**/*.test.ts` — see that app's guide; `core/` is framework-free by necessity |

`aow5-api-contract` has no tests: it is type declarations and numbers, and `tsc` is the check.

Node strips types but **not JSX**, so anything worth testing goes in a JSX-free module and the component
imports it. `src/lib/routes.ts` is the pattern: it was split out of `router.tsx` for exactly this reason.

If your change touches encoding, decoding, the id tables or routing, it needs a test. If it is layout or
copy, screenshots in the PR are the evidence instead.

## Branches and commits

Branch off `master`. Name it `<area>/<slug>` — `builder/faceted-search`, `site/ru-copy-pass`,
`fix/share-bar-overflow`.

Commit subjects match what is already in the log: one line, capitalized, no trailing period, saying what
changed rather than which files moved — *"Reworked the tracker HUD around the current room"*. Put the
*why* in the body when the subject cannot carry it. Keep a PR to one coherent change; a data refresh, a
dependency bump and a feature are three PRs.

## Opening the pull request

The description is the review. This repo's READMEs explain why things are the way they are, and a PR is
where that explanation starts — a reviewer should be able to tell what changed, what it will do to
somebody's existing link, and what you deliberately left out, without opening the diff.

Copy this into the description and fill it in. Delete a section only when it is genuinely not applicable,
and say so rather than leaving it blank.

````markdown
## What

One or two sentences: the feature as a user of the planner would describe it.

## Why

The problem it solves, or the thing that was awkward before. If there is an issue, link it.

## How it works

The shape of the implementation and the one or two decisions a reviewer would otherwise
have to reverse-engineer — why this component and not that one, what you tried first.

## Share-link impact

- Codec version: unchanged / bumped to vN
- id-table / ability-table: untouched / appended N entries (pipeline run: yes/no)
- Existing links: what a v6 link does after this change
- New golden test: file and what it pins

## Copy and languages

Keys added or changed, in strings.ts / site.ts, EN + RU + ZH. "None" is a valid answer.

## Screenshots

Light and dark. Include the empty, filled and error states if the change has them.

## Testing

- [ ] `pnpm check-types`
- [ ] `pnpm test`
- [ ] `pnpm build`
- Manually: what you clicked, in which browser, and what you checked on a narrow window.

## Scope left out

What you knowingly did not do, and why — the follow-up someone else would otherwise
open as a bug.
````

A filled-in *Share-link impact* looks like this, and takes ten seconds:

```markdown
## Share-link impact

- Codec version: unchanged (v6) — the note rides in the existing descriptions segment
- id-table / ability-table: untouched
- Existing links: decode identically; a v6 link with no note round-trips to the same bytes
- New golden test: "a note past the 160-character cap is rejected before encoding"
```

## What gets a PR sent back

- a wire-format change with no version bump, or no golden test for it
- English-only strings, or a string hardcoded in a component
- a feature that only looks right in one theme
- a new runtime dependency with no argument for its weight
- regenerated data or `dist/` files riding along with a feature
- a description that says *"adds faceted search"* and nothing else

## Before you build something large

Open an issue first for: a new route, a codec version, a new runtime dependency, anything that changes the
extraction pipeline, or anything that would make this app and the tracker know about each other. The
README's *Scope* section lists what is already planned — faceted browsing by category and tier,
drag-and-drop between slots — and picking one of those up needs no discussion beyond saying you are on it.

Small fixes, copy, translations and tests: just open the PR.
